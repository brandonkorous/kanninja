Why build it

An AI-first kanban
needs an AI-first surface.

Three arguments. Any one of them would be enough on its own. The combination is the tell.

01 · positioning

It fits the product

kanNINJA leans hard into AI — twelve native capabilities, the dojo-kata-clan vocabulary, the whole katana thing. An MCP server is the most honest expression of that positioning: the product reaches users where they already work, rather than demanding a context switch to a browser tab.

02 · distribution

Cheap acquisition

Anthropic's MCP directory, Smithery, and the plugin panels in every MCP-aware IDE are low-cost surfaces for exactly the audience that pays for Pro+. Terminal-native developers discover tools by typing add kanNINJA — and never see your landing page.

03 · conversion

Natural tier pull

Free CRUD tools (read boards, move tasks, add comments) anchor adoption. AI-native tools — break down epics, estimate kata, draft standup — sit behind Pro+. Usage pushes users up the ladder organically instead of asking marketing to do the lifting.

System architecture

One package, two deploy modes.

The interesting line is between local stdio (ship fast, user brings their own key) and remote HTTP+SSE (one-click add, OAuth, billable). Both share a single tool registry that reuses the Fastify API contracts — no duplication.

Auth flows

Two auth paths. Same contract.

The backend treats an API key and an OAuth access token as equivalent credentials at the API layer. Which transport the call arrived through is irrelevant to Fastify — authentication happens once, tier enforcement happens every time.

Local stdio · API key

mode A — ships in Phase 2a
  1. Generate key in kanNINJA settings. Format ninja_live_…. Scoped to a single workspace.
  2. Add to client config. In claude_desktop_config.json or mcp.json: env: { KANNINJA_API_KEY }.
  3. Client boots subprocess. Claude Code runs npx @kanninja/mcp as a stdio child process on demand.
  4. Package authenticates. Reads key from env, attaches Authorization: Bearer on every Fastify call.
  5. Backend verifies. POST /v1/auth/verify-key returns user + workspace + tier, cached for the subprocess lifetime.
  6. Tool calls proxy through. Every invocation is a regular REST call with the cached credential.

Remote HTTP · OAuth

mode B — ships in Phase 2b
  1. User adds server at https://mcp.kanninja.com in Claude.ai or ChatGPT desktop.
  2. Server returns 401 with WWW-Authenticate: Bearer header and OAuth metadata discovery URL.
  3. Client redirects to Clerk's authorize endpoint with kanNINJA's client ID and required scope list.
  4. User consents to scopes: read:boards, write:tasks, ai:capabilities, team:read.
  5. Clerk returns tokens. Server stores refresh token; client receives short-lived JWT access token.
  6. Tool calls authenticated as user. Every request carries the JWT; Fastify validates signature, expiration, and scope.
Tool surface

Four categories. One vocabulary.

Every tool name reads as a verb against a board concept. Free tools move data. Pro+ tools think about it. Team+ tools coordinate across people.

Read — query

Free · all tiers
  • list_boardsall dojos visible to the caller
  • get_boardcolumns, tasks, members, recent activity
  • list_tasksfiltered by status, assignee, due, label, clan

Canonical example

Anatomy of one tool: break_down_task.

The most interesting tool to spec because it's AI-native, Pro-gated, streams in hosted mode, calls into the backend AI capability layer, writes an audit entry, and meters usage. If you can ship this cleanly, the other five AI tools fall out.

break_down_task

v2/mcp-server/src/tools/ai/breakDownTask.ts

Given a task that's too large to act on, return 3–8 subtasks with titles, acceptance criteria, and rough estimates. Posts the result as a threaded comment on the parent and — if the caller opts in — creates the subtask records directly.

Streams token-by-token in hosted mode over HTTP+SSE. In local stdio mode it buffers and returns once, because MCP stdio doesn't yet support streamed tool output.

Tier gate
Pro, Team, or Enterprise. Returns 402 on Starter / Builder with an upgrade prompt in the error message.
Cost model
Metered per call. Deducted from the workspace AI credit balance — hard-capped, not billable beyond plan allowance.
Side effects
Comment created on parent task. Optional subtask creation if apply: true. Full input and output recorded in audit_log for Team+ workspaces.
Telemetry
Tool name, tier, latency, token count, acceptance (did the user apply the suggestion?). Feeds the AI-tool product funnel dashboard.
breakDownTask.ts
import { z } from 'zod';
import { defineTool, requireTier } from '../../registry';
import { callApi } from '../../api';

// Shared with the Fastify route at /v1/ai/break-down-task
const input = z.object({
  taskId: z.string().uuid(),
  maxSubtasks: z.number().int().min(2).max(12).default(6),
  apply: z.boolean().default(false),
  style: z.enum(['lean', 'detailed']).default('lean'),
});

const output = z.object({
  parentTaskId: z.string().uuid(),
  subtasks: z.array(z.object({
    title: z.string().min(1).max(140),
    acceptanceCriteria: z.array(z.string()).min(1),
    estimateHours: z.number().nullable(),
  })).min(2).max(12),
  applied: z.boolean(),
  commentUrl: z.string().url(),
});

export default defineTool({
  name: 'break_down_task',
  title: 'Break a task into subtasks',
  description:
    'Decompose an epic into 3–8 actionable subtasks. Posts a' +
    ' comment on the parent and optionally creates the subtasks.',
  tier: requireTier('pro'),
  inputSchema: input,
  outputSchema: output,

  async handler(args, ctx) {
    // The Fastify route does the AI work, writes audit log,
    // and meters usage. The MCP tool is deliberately thin.
    return callApi(ctx, 'POST', '/v1/ai/break-down-task', args);
  },
});

Phase roadmap

Three ships. Each one justifies the next.

Ship small, prove demand, add the moat. Don't build AI tools before anyone is using basic CRUD over MCP — you'll build the wrong ones. Local first is the cheap way to find out what people actually reach for.

Phase 2a · v0.1

Local stdio — ship it fast.

Get a working MCP server into real users' hands with minimum infrastructure. No hosted endpoint, no OAuth, no billing integration. Just an npm package that speaks stdio to any MCP client, authenticated with an API key.

  • New package at v2/mcp-server/ using @modelcontextprotocol/sdk
  • API-key auth only; backend adds POST /v1/auth/verify-key plus a key management UI
  • Free-tier tools: all Read and most Write (no create_board on free tier)
  • Zod-to-MCP schema adapter in shared/mcp-schema.ts (≈ 50 lines)
  • Published to npm as @kanninja/mcp and submitted to Smithery
Ship criteriaUser can go from landing page to working tools inside a Claude Code session in under two minutes.
Phase 2b · v0.3

Hosted remote — one-click add.

Deploy mcp.kanninja.com with Clerk OAuth plus Stripe-gated access. This is the version people actually adopt from Claude.ai without ever touching a config file.

  • Fastify service at mcp.kanninja.com with HTTP + SSE transport
  • Clerk OAuth 2.0 with scopes read:boards, write:tasks, ai:capabilities, team:read
  • Stripe subscription check cached in Redis (30 s TTL) on every request
  • Published to the Anthropic MCP directory and Smithery hosted tier
  • Per-tier rate limits enforced at the Fastify layer via existing Redis buckets
Ship criteriaUser adds kanNINJA to Claude.ai in a single click and OAuth consent takes one tap.
Phase 3 · v1.0

AI-native tools — the moat.

The tools that make kanNINJA worth choosing over Linear's MCP server. Everything else is commodity; these are the product.

  • Ship all six AI-native tools backed by existing /v1/ai/* capability routes
  • Clan tools gated behind Team tier, respecting existing RBAC
  • Per-workspace AI credit metering integrated with billing
  • Telemetry feeds a Metabase dashboard: tool acceptance rate, tier pull-through, churn correlation
  • Audit log for Team+ records full input and output for compliance review
Ship criteriaAt least 40 % of Pro+ subscribers invoke one AI tool per week within 30 days of launch.
Open questions · risks

The things I can't answer yet.

Each of these could be small. Each of them could also become the thing that blocks the launch. Flagging early so they get answered on purpose, not by default.

01 · AI cost ceiling

Chatty clients will happily burn tokens. Who pays for the LLM calls when a Claude Code session runs break_down_task on twenty kata in a row? Hard monthly caps per tier, or usage-metered with overage billing? Decide before Phase 3 starts.

02 · Schema drift during Phase 1

Fastify contracts will churn during Core Kanban CRUD work. MCP users are external consumers — breaking changes have real cost. Semver plus a two-version deprecation window, or freeze the MCP tool surface against the last stable Phase 1 milestone?

03 · Compliance and audit

Team+ customers will want to know what an MCP call did on their behalf. Every mutation needs a structured audit entry plus a viewer in the web app. Could be a week of work alone — scope it into 2b, or wait for 3?

04 · Differentiation from Linear

Linear already ships an MCP server. Matching them on CRUD is commodity work. Phase 3's AI tools are the only real reason to choose kanNINJA — so Phase 3 can't slip, and its tools can't be table-stakes clones of each other's output.

05 · Local vs remote priority

Most competitors ship remote-hosted first because it drives direct conversion. We're flipping that: local stdio is cheaper and lower risk, and it lets us validate tool design before committing to OAuth infrastructure. Worth re-checking this bet before 2a kicks off.

06 · API key revocation UX

Stolen API key equals workspace exposure. Self-service rotation, list of active sessions, "revoke all" button. Not technically hard — but it must exist on day one of Phase 2a or we ship a security footgun.

Next steps

Six concrete moves, in order.

None of these require the Phase 1 CRUD backend to be finished. They're the preparation that lets Phase 2a ship the day Phase 1 lands.

  1. Design Fastify routes with MCP in mind During Phase 1, give /v1/* resources stable names and shared Zod schemas in shared/ even before the MCP package exists. Zero extra cost now, months saved later.
  2. Write the Zod → MCP adapter A ~50-line utility in shared/mcp-schema.ts that turns any z.object(...) into an MCP inputSchema. Unit-test it against a dozen existing Zod objects.
  3. Spec the API-key data model api_keys table: id, user, workspace, scopes, display prefix, hashed secret, last_used_at, revoked_at. RLS plus a service for create, list, verify, revoke.
  4. Prototype @kanninja/mcp locally Against a staging workspace, with just two tools: list_boards, get_board. Verify the full path — stdio → package → Fastify → Drizzle → response rendered in Claude Code.
  5. Decide cost and rate-limit policy One-page doc covering write-tool limits by tier, AI tool cost model, overage behavior. Needs sign-off before Phase 2a build starts — this shapes the billing code.
  6. Reserve namespaces Register @kanninja/mcp on npm, mcp.kanninja.com DNS, and submit a stub listing to Smithery. Cheap, prevents squatting.
